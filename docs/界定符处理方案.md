在实现 Markdown 编辑器时，处理成对定界符（如加粗 `**bold**`）的核心是：**始终保证定界符成对出现，避免出现单个 `*` 或破坏语法**。下面以加粗为例，分别从“未选中”和“选中”两种状态，结合光标在文字段前、中间、末尾三个位置，给出交互算法。

## 1. 模型定义

假设已有文本：

```
**加粗**
```

它由以下部分组成：

| 索引 | 内容 |
|------|------|
| 0    | `*` 起始定界符第 1 位 |
| 1    | `*` 起始定界符第 2 位 |
| 2    | `加` 文字 |
| 3    | `粗` 文字 |
| 4    | `*` 结束定界符第 1 位 |
| 5    | `*` 结束定界符第 2 位 |

光标位置用 `offset` 表示（位于字符之间，0 到 6）。
选区用 `[s, e)` 表示，包含 `s` 但不包含 `e`。

一个加粗范围可以表示为：

```ts
type BoldRange = {
  openStart: number;   // 起始定界符的第一个 '*'
  openEnd: number;     // 起始定界符后，文字开始
  closeStart: number;  // 结束定界符前，文字结束
  closeEnd: number;    // 结束定界符的最后一个 '*'
};
```

对于 `**加粗**`：

```
openStart = 0
openEnd = 2
closeStart = 4
closeEnd = 6
```

## 2. 未选中时的交互算法

未选中时只有光标，我们关注三个位置：

- **前**：光标在起始定界符之前，例如 `|**加粗**`，`offset = 0`
- **中**：光标在加粗文字内部，例如 `**加|粗**`，`offset = 3`
- **后**：光标在结束定界符之后，例如 `**加粗**|`，`offset = 6`

### 2.1 光标在文字段前（offset = 0）

#### 普通输入
用户直接输入普通字符，字符插入在加粗范围之外：

```
输入 'x'  ->  x|**加粗**
```

不需要特殊处理，定界符仍然配对。

#### 点击加粗按钮（或 Ctrl+B）
此时光标不在任何加粗范围内。常见的处理是插入一对空加粗标记 `****`，并将光标放在中间：

```
插入前： |**加粗**
插入后： ****|**加粗**
```

光标位于 `****` 的中间，接下来输入的字符会被加粗。

如果做优化，可以检查光标右侧是否紧跟一个已有加粗范围，若是，则可以将新输入合并到该范围中，避免产生相邻的 `****` 片段。但简单产品可以先不做合并。

#### 删除 / 退格
- 退格：offset = 0 时没有前一个字符，无操作。
- Delete：删除第一个 `*` 时，如果检测到它属于起始定界符，则应该**成对删除**：
  - 同时删除起始定界符的两个 `*`（索引 0、1）
  - 同时删除结束定界符的两个 `*`（索引 4、5）
  - 结果变成 `加粗`，光标留在原文字开始处。

这样避免了留下单个 `*` 或孤立的结束定界符。

---

### 2.2 光标在文字段中间（offset = 3）

#### 普通输入
用户输入普通字符，字符直接成为加粗内容：

```
输入 'x'  ->  **加x|粗**
```

不需要特殊处理。

#### 点击加粗按钮
光标已经处于加粗范围内部，点击加粗按钮通常会**取消加粗**：

```
操作前： **加|粗**
操作后： 加|粗
```

实现时：

1. 删除起始定界符 `**`（索引 0、1）
2. 删除结束定界符 `**`（注意左侧删除后索引会变化，结束定界符位置左移 2）
3. 光标位置左移 2（因为起始定界符被删除）

#### 删除 / 退格

- 退格删除文字内容中的字符，不影响定界符。
- 如果退格一直删除到文字开头（例如 offset = 2），再退格会删除起始定界符的第二个 `*`。此时应触发成对删除：
  - 同时删除起始定界符的两个 `*`
  - 同时删除结束定界符的两个 `*`
  - 结果变成 `加粗`
- 同理，在 offset = 4 时按 Delete 会删除结束定界符的第一个 `*`，也应触发成对删除。

---

### 2.3 光标在文字段末尾（offset = 6）

#### 普通输入
用户输入普通字符，字符插入在加粗范围之外：

```
输入 'x'  ->  **加粗**x|
```

不需要特殊处理。

#### 点击加粗按钮
光标位于加粗范围之外，点击加粗按钮插入空加粗标记：

```
操作前： **加粗**|
操作后： **加粗****|
```

光标位于新插入的 `****` 中间，后续输入会加粗。

如果做优化，可以检查光标左侧是否紧邻已有加粗范围，若是则可以合并。

#### 删除 / 退格

- 退格删除最后一个 `*`（offset = 6 时退格会删除索引 5 的 `*`）。检测到它属于结束定界符，应成对删除：
  - 同时删除结束定界符的两个 `*`
  - 同时删除起始定界符的两个 `*`
  - 结果变成 `加粗`
- 如果退格删除的是文字末尾的字符（例如 offset = 4 时退格删除“粗”），则不影响定界符。

## 3. 选中时的交互算法

有选区时，主要关注选区与已有加粗范围的关系。设选区为 `[s, e)`。

### 3.1 选区在文字段前（整个选区在 `**加粗**` 之前）

例如文档：

```
abc|**加粗**
```

选中 `abc`，选区为 `[0, 3)`。

点击加粗按钮：

- 选区未加粗，因此在选区前后插入定界符：

```
结果： **abc**|**加粗**
```

如果做优化，可以检测到两个加粗范围相邻，合并为：

```
**abc加粗**
```

这取决于产品需求；Markdown 渲染效果相同，但源码更干净。

---

### 3.2 选区在文字段中间（选区完全在加粗范围内）

例如文档：

```
**加|粗**
```

选中文字 `粗`，选区为 `[3, 4)`（假设索引 2 为“加”、3 为“粗”）。

点击加粗按钮：

- 选区完全在加粗范围内，应当**取消加粗**。
- 删除起始定界符和结束定界符：

```
结果： 加|粗
```

选区位置左移 2（因为起始定界符被删除），选中文字本身不变，但已经不再加粗。

如果选中了整个加粗文字（`加粗`，选区为 `[2, 4)`），结果同样取消整个加粗范围。

---

### 3.3 选区在文字段末尾（整个选区在 `**加粗**` 之后）

例如文档：

```
**加粗**abc|
```

选中 `abc`。

点击加粗按钮：

- 选区未加粗，在选区前后插入定界符：

```
结果： **加粗****abc**
```

同样可以优化合并为 `**加粗abc**`。

---

### 3.4 选区跨定界符或部分重叠

例如选区从 `**加` 到 `粗**`，或者选区包含了一个定界符的一部分。

这种情况下，为了保持定界符配对，推荐使用以下**稳定策略**：

1. **移除所有与选区相交的加粗范围**。
   即删除这些范围的起始定界符和结束定界符，但不删除文字内容。
2. **调整选区位置**。
   因为删除了定界符，选区偏移会发生变化，需要重新计算。
3. **在选区的前后插入新的 `**`**。
   这样选区文字会重新变成加粗，且定界符配对正确。

例如文档：

```
**加粗** 后面选中了粗** 一部分
```

简化处理：
- 先取消涉及的加粗，得到纯文本 `加粗`
- 再对选区重新包裹 `**`。

该策略可能导致一些加粗范围被合并或修改，但实现简单，且不会产生不匹配的定界符。

---

## 4. 删除/退格的成对保护算法

在编辑有定界符的文本时，最容易破坏语法的情况是**删除单个定位符**。建议实现以下保护：

### 判断某个 `*` 是否属于加粗定界符的一部分

```
isDelimiterStar(pos):
    if text[pos] != '*': return false
    # 向左找最近的 '**'，向右找最近的 '**'
    # 如果该 '*' 是某个加粗范围 openStart/openEnd 或 closeStart/closeEnd 的一部分，则返回 true
```

### 删除操作扩展

当用户执行 Backspace 或 Delete 时，如果目标字符是 `*` 且属于加粗定界符：

- **删除起始定界符中的任意一个 `*`**：同时删除起始定界符的另一个 `*`，以及对应的结束定界符的两个 `*`。结果是取消整个加粗范围。
- **删除结束定界符中的任意一个 `*`**：同时删除结束定界符的另一个 `*`，以及对应的起始定界符的两个 `*`。

这样用户无论从哪个方向删除，都能一次性移除成对的定界符，避免出现单个 `*` 或孤立的 `**`。

## 5. 伪代码示例

以下是一个简化的 `toggleBold` 实现，展示核心逻辑：

```ts
type Range = {
  openStart: number;
  openEnd: number;
  closeStart: number;
  closeEnd: number;
};

function toggleBold(doc: string, sel: { start: number; end: number }) {
  if (sel.start !== sel.end) {
    return toggleBoldSelection(doc, sel);
  } else {
    return toggleBoldCursor(doc, sel.start);
  }
}

function toggleBoldCursor(doc: string, pos: number) {
  const range = findBoldAt(doc, pos);

  if (range && pos >= range.openEnd && pos <= range.closeStart) {
    // 光标在加粗内部：取消加粗
    doc = removeRange(doc, range.openStart, range.openEnd);      // 删除起始 '**'
    doc = removeRange(doc, range.closeStart - 2, range.closeEnd - 2); // 删除结束 '**'
    return { doc, pos: pos - 2 };
  } else {
    // 光标在加粗外部：插入空加粗标记
    doc = insert(doc, pos, '****');
    return { doc, pos: pos + 2 };
  }
}

function toggleBoldSelection(doc: string, s: number, e: number) {
  const ranges = findBoldRangesIntersecting(doc, s, e);

  if (ranges.length === 0) {
    // 选区未加粗：包裹
    doc = insert(doc, e, '**');
    doc = insert(doc, s, '**');
    return { doc, sel: { start: s, end: e + 4 } };
  }

  // 检查选区是否完全在某个加粗范围内
  const r = ranges[0];
  if (ranges.length === 1 && s >= r.openEnd && e <= r.closeStart) {
    // 选区完全在加粗内部：取消加粗
    doc = removeRange(doc, r.openStart, r.openEnd);
    doc = removeRange(doc, r.closeStart - 2, r.closeEnd - 2);
    return { doc, sel: { start: s - 2, end: e - 2 } };
  }

  // 部分重叠：先移除所有相交的加粗范围，再重新包裹选区
  let adjustedS = s;
  let adjustedE = e;

  // 按起始位置从后往前删除，方便调整偏移
  const sorted = ranges.sort((a, b) => b.openStart - a.openStart);
  for (const r of sorted) {
    doc = removeRange(doc, r.openStart, r.openEnd);
    doc = removeRange(doc, r.closeStart - 2, r.closeEnd - 2);
  
    // 调整选区偏移
    if (r.openStart < adjustedS) adjustedS -= 2;
    if (r.openStart < adjustedE) adjustedE -= 2;
    if (r.closeStart - 2 < adjustedS) adjustedS -= 2;
    if (r.closeStart - 2 < adjustedE) adjustedE -= 2;
  }

  doc = insert(doc, adjustedE, '**');
  doc = insert(doc, adjustedS, '**');

  return { doc, sel: { start: adjustedS, end: adjustedE + 4 } };
}
```

实际实现中还需要处理转义、嵌套等复杂情况，但以上伪代码覆盖了基本场景。

## 6. 总结

| 位置 | 未选中（光标） | 选中（选区） |
|------|---------------|--------------|
| **前**（`|**加粗**`） | 输入普通字符在外侧；点击 B 插入空标记 `****` | 选区未加粗，包裹 `**` |
| **中**（`**加|粗**`） | 输入成为加粗内容；点击 B 取消加粗 | 选区完全在加粗内部，取消整个加粗 |
| **后**（`**加粗**|`） | 输入在外侧；点击 B 插入空标记 `****` | 选区未加粗，包裹 `**` |
| **跨边界** | — | 移除相交定界符后重新包裹 |

此外，删除操作应实现**成对定界符保护**，避免用户只删除一个 `*` 导致 Markdown 语法错误。

这样的交互算法可以保证用户在编辑加粗文字时，定界符始终配对，编辑体验符合常见 Markdown 编辑器的预期。

# 附：MDA 实际实现（以此为准）

> 上文是外部 AI 给出的参考方案。MDA 的落地实现在其基础上做了两点关键强化：
> **① 判据从「定界符成对」提升为「预览可见文本里不出现任何裸定界符」**；
> **② 相邻同类样式段一律融合，而不是各自保留一对定界符。**

## A. 为什么判据要更严

MDA 预览模式下定界符**始终隐藏**（D15 策略，`hide-mark` 装饰替换为零宽 widget）。
因此 `**A****B**` 这种「每一对都合法配对」的文本，在预览里会渲染成 `A****B` ——
中间 4 个星号既不是任何样式段的定界符（成对但空内容），又落在可见区，直接泄漏给用户。

所以验收判据不是「`*` 数量为偶数」，而是：

> 把全部 `hide-mark` / `hide-line` / widget 覆盖区从源码里挖掉之后，
> 剩下的**可见文本**中不得出现 `*` / `~` / `` ` `` 这类定界符字符。

单测里统一用 `visibleText(doc)` 计算该值（见 `tests/gui/editor/inline-delimiter-ops.test.ts`）。

## B. 三层结构

| 层 | 文件 | 职责 |
|----|------|------|
| 规划（纯函数） | `editor/model/inline-delimiters.js` | 融合包裹 / 拆分取消 / 空对清理 / 隐藏 run 跳过，无 DOM 无 EditorView |
| 取材 | `editor/state/inline-mark-context.js` | 从语法树按**行窗口**收集 `MarkRegion` 与定界符 run |
| 接线 | `editor/state/inline-delimiter-ops.js` | 映射区段坐标、派发事务、挂 keymap |

`MarkRegion` 统一描述一个样式段：`{ key, open, content, close }`，五类标记
（bold `**` / italic `*` / underline `~` / strike `~~` / code `` ` ``）共用该结构。

## C. 四条核心算法

### C1 融合包裹 `planFusedWrap`

把 `[from,to)` 变成样式段时，**相交或紧邻**（`close.to === lo` 或 `open.from === hi`）的同类样式段
一并吸收：先把被吸收段的全部定界符从内容里剔除，再在融合后的整体两端补**一对**定界符。

```
**加粗**尾巴   选中「尾」加粗   ->  **加粗尾**巴      （不是 **加粗****尾**巴）
AA**BB**CC     整行加粗         ->  **AABBCC**       （不是 **AA****BB****CC**）
```

内容为空则**不生成**定界符对（杜绝裸 `****`）。

### C2 拆分取消 `planSplitUnwrap`

选区只覆盖样式段的一部分时，不再「什么都不做」，而是拆成两段：
左侧残段在选区起点补闭定界符，右侧残段在选区终点补开定界符；
残段为空则把对应的整对定界符删掉，绝不留下空对。

```
**加粗文字**   选中「粗文」取消  ->  **加**粗文**字**
**加粗文字**   选中「加粗文字」  ->  加粗文字
```

同一次调用可以跨多种标记（清除格式即传入全部五类样式段）。

### C3 清理 `planRegionCleanup`

给**非规划器产生**的变更（删除、剪切、粘贴、待输入插入）兜底，在同一次派发的
第二段事务里执行。三条规则：

1. 内容被掏空（`content.to <= content.from`）→ 整对定界符删除；
2. 定界符被编辑吃掉一部分（映射后长度与编辑前不一致）→ 该段两侧残余一并删除；
3. 同类样式段紧邻（中间只剩已被删掉的定界符）→ 删掉贴在一起的「闭+开」，融合成一段。

**清理必须回避被本次变更重写过的定界符**：判据是「映射后长度与变更前不一致」。
待输入插入、输入法上屏都会重写定界符（例如把「内容+闭定界符」整段替换掉），
此时区段的新形态由变更方负责；若拿变更前的坐标去清理，会把**刚写进去**的定界符
当成残余删掉——现象是整段样式连同新输入的文字一起消失。

由此带来的空缺（删除区间只吃掉一侧定界符 → 另一侧裸露）改在**源头**堵，见 §C3b。

### C3b 删除区间规划 `planDeleteRangePreservingPairs`

预览里定界符不可见，而点击落点校准是**不对称**的（`caret-syntax-adjust.js`：
左缘推到开定界符**外侧**、右缘停在闭定界符**内侧**）。所以「从段首往中间拖选」时，
用户看到自己只选了正文，选区实际却已经把开定界符吃进去了，直接删就剩下裸露的闭定界符：

```
**加粗**  从可见左缘选到「加」之后按 Delete  ->  粗**    （错，闭定界符裸露）
```

不能反过来「撑到整对」——那会把用户没选中的可见文字（「粗」）一起删掉。正确做法是
**把删除区间按定界符切成多段**，跳过需要保留的定界符：

| 区间与样式段的关系 | 处理 |
|--------------------|------|
| 整对定界符都在区间内 | 连定界符一起删 |
| 内容被整段覆盖、定界符在区间外 | 定界符也吃掉，不留空对（仅**纯删除**；见下） |
| 只覆盖一侧定界符 | **原样保留**该定界符，区间从它两边绕过去 |

```
**加粗**  选 [开定界符左侧, 「加」之后]  ->  删 ["加"]        ->  **粗**
**加粗**  选 [「粗」之前, 闭定界符右侧]  ->  删 ["粗"]        ->  **加**
AA**加粗**  选 [0, 「加」之后]           ->  删 ["AA"]["加"] ->  **粗**
```

第二条只适用于**纯删除**：若区间随即被新文本替换（粘贴、替换输入），掏空的样式段又会
被填满，此时删掉定界符等于顺手取消了用户的样式，须传 `collapseEmptied = false`
（`**加粗**` 选中内容粘贴 `X` → `**X**`，而不是 `X`）。

### C4 隐藏 run 跳过 `skipHiddenRuns`

定界符在预览里不可见，光标「贴着」它时按 Backspace/Delete 必须作用到**可见字符**，
而不是把定界符删掉半个。`deleteAcrossDelimiters` 先跳过隐藏 run 再按
`findClusterBreak` 删一个字素簇，最后交给 C3 清理。

```
AA**粗**BB  光标在结束定界符之后按退格  ->  AABB    （不是 AA**粗*BB 或 AA****BB）
```

## D. 入口接线

| 入口 | 走向 |
|------|------|
| Ctrl+B/I/U 等、工具栏，**无选区** | `togglePendingInlineMark`（待输入层），插入时经 `dispatchTypedInsertWithCleanup` |
| 同上，**有选区** | `applyInlineMarkToSelection` → C1/C2 → `dispatchPlannedChange`（规划器输出已干净，不再叠加清理） |
| 输入法上屏（`compositionend`） | `planCompositionEndReplace` → 见 §D1 |
| Backspace / Delete（预览模式 `Prec.high` keymap） | 无选区 → C4 + C3；有选区 → C3b + C3 |
| 剪切 / 标题行粘贴 | `replaceRangeWithCleanup` → 端点外推 + C3b + C3 |
| 清除格式，有选区 | `planClearInlineMarks`（五类一起走 C2）+ 第二段事务做块级清理 |

**跨标记混排选区不再折叠**：旧实现遇到「选区两端行内样式不一致」会把选区收成光标、
只改待输入状态，用户观感是「点了没反应」。现在统一交给规划器，跨加粗/斜体、
整行混排、嵌套样式都能正确融合或拆分。

**无选区切换须一次到位**（`planPendingMarkToggle`，`inline-mark-context.js`）：
定界符在预览里不可见，所以「内容首/尾」（`inside && pos === content.from|to`）与
「开/闭定界符外侧」（`head-out` / `tail-out`）在屏幕上是**同一个点**。这两个边界分支早先只把
光标挪到定界符外、`marks` 保持不变 —— 挪完之后待输入格式仍然是开的，融合规则会让输入照样进段内，
于是用户看到的是**第一次点击毫无反应，要点两次才切换**。现在与 head-out/tail-out 对称：
开着就关掉并把光标推到定界符外侧，关着就打开、光标留在内容里。回归见
`tests/e2e/gui/inline-delimiter-edit.spec.ts` 的 E-INL-4（五种标记 × 段头/段尾）。

**拆分取消须过渲染探针**（`repairUnrenderableSplit`，`pending-inline-format.js`；
探针函数 `textRangeHasMarks` 在 `markdown-probe.js`，独立模块是为断 `inline-string-ops`
↔ `pending-inline-format` 的加载期环依赖）：

`**、加粗**` 在段内取消样式时，朴素拆分产出 `**、**测试**粗**`：每对定界符都配对，
但 CommonMark 的 flanking 规则让闭定界符左邻为标点时**无法闭合**，解析器会把它与后续
`**粗**` 重新配成**外层**强调 —— 用户按了「取消」却整串变粗；第二次输入还会在缝隙里
再拆一次，留下裸 `****`。`bold`/`italic`/`strike` 均中招（自定义 `~` 下划线不受影响）。

规划器在 `buildPendingTypedInsert` 末尾用探针校验：插入文字是否**真的**无该样式、保留下来的
残段是否**真的**仍有样式。失败则按「原方案 → 解左残段 → 解右残段 → 两边都解」取第一个
能渲染的方案（常见结果：`、测试**加粗**`）。回归见 E-INL-5、`table-cell-punct-cancel.spec.ts` 与
`pending-inline-format.test.ts`「顿号紧贴开定界符」。

### D1 输入法上屏必须在「干净文档」上规划

键盘输入走 `EditorView.inputHandler`，此时字符**还没进文档**，`buildPendingTypedInsert`
面对的是原始文档，落点算得准。输入法不同：`compositionend` 触发时，组字文本
（可能还带拼音残留）**已经落在光标处**，文档结构被临时破坏。

旧实现直接在这份被污染的文档上算落点，再把 `[spec.from, deleteTo)` 合并成**一个区间**
替换掉——夹在落点与组字文本之间的定界符被连带吞掉：

```
尾后上屏  AA**文字**|  +「测试」 ->  AA**文字测试BB      闭定界符没了
头前上屏  |AA**文字**  +「测试」 ->  AA**测试****文字**BB  多出一对
```

正确做法是先把组字污染区整段摘掉，得到与键盘输入等价的**干净文档**，在其上规划，
再把结果换算回当前坐标——换算时必须把落点与组字区之间的原文**一并带上**，
否则又会退化成吞字符：

```js
const cleanState = state.update({ changes: { from: deleteFrom, to: deleteTo, insert: '' } }).state;
const spec = buildPendingTypedInsert(cleanState, deleteFrom, deleteFrom, data, intended);
// spec.from <= deleteFrom：insert = spec.insert + clean[spec.from, deleteFrom)
// spec.from >  deleteFrom：insert = clean[deleteFrom, spec.from) + spec.insert，右端 +（deleteTo-deleteFrom）
```

这样「拼音残留清理」「取消样式后拆分」「头尾并入」三种情形都由同一条路径覆盖，
不再需要 `needs` / `hasImeJunk` 分支；结果与原文一致时返回 `null`，避免多余历史项与 IME 抖动。

### D2 干净文档是**替换路径**的规范，不只是 compositionend

上面这套只挂在 `planCompositionEndReplace` 上时，真实中文输入法**根本走不到**：

- 组字阶段落进文档的是**拼音字母**（`ce'shi`），不是最终汉字；
- `compositionend` 触发时 CM6 的 state 里仍是拼音，`findCommittedText` 找不到 `data`，
  `planCompositionEndReplace` 直接以 `noCommittedTextOrRange` 拒绝；
- 真正干活的是随后的 `inputHandler`，参数是「**用汉字替换掉那段拼音**」
  （`from=15, to=21, text='测试'`）。

而 `handlePendingInput` / `applyPendingTypedInsert` 当时仍在**当前文档**上取材，
那段待删的拼音恰好夹在光标与定界符之间，`resolveMarkRegion` 找不到紧邻的样式段，
于是把「延续已有样式」误判成「新包一层」：

```
docSnap  、|ce'shi**加粗**     ->  、**测试****加粗**
```

所以干净文档不是 IME 专属技巧，而是**所有 `from < to` 的替换路径**的规范。现由
`planTypedReplace(state, from, to, text, intended)` 统一承担（`from === to` 时退化为
直接规划），`planCompositionEndReplace` 与 `applyPendingTypedInsert` 都调它；
`handlePendingInput` 的放行判断（`canPassThroughPendingInput`）也须用
`typedReplaceBasis` 取同一份干净文档——放行等价于「CM6 把 text 插到干净文档的 from 处」。

**用最终汉字当组字文本的模拟测不出这条**：那样 `findCommittedText` 会成功，
于是走的是 `planCompositionEndReplace`，恰好绕开了出问题的替换路径。
单测须模拟拼音先落盘（`tests/gui/editor/inline-input-sweep.test.ts` 的 `IME拼音` 模式），
e2e 须用 CDP 逐字送拼音再 `insertText` 汉字。

## D3. 表格单元格：同一套规划器，另一条接线

单元格是 widget 内的 `contenteditable`，内容以 **Markdown 字符串**形态存在，
没有 CM6 文档可依托。早期因此另接了 `editor-assist` 的朴素 wrap/unwrap，
结果 C1/C2/C3 这些规则在格内一条都不生效：选中加粗段中间取消会留下裸 `**`，
在样式段头前带格式输入会插出 `**测试****加粗**`。

现由 `state/inline-string-ops.js` 用**一次性 EditorState** 搭桥：

```
textState(text) = EditorState.create({ doc: text, extensions: [markdown({extensions: GFM})] })
                  + ensureSyntaxTree(...)   // 不预热则短文本也可能拿到空树
```

在其上直接复用 `collectMarkRegions` / `collectDelimiterRuns` / C1 / C2 / C3。
单元格内容短、这些操作又都由点击或按键驱动（非逐帧），临时建 state 的开销可以接受。

| 场景 | 格内入口 | 复用的规划 |
|------|----------|------------|
| 有选区切换标记 | `toggleInlineMarkInText` | 全覆盖 → C2 拆分取消；否则 C1 融合包裹 |
| 无选区待输入 | `planTypedInsertInText` | `buildPendingTypedInsert` + C3 清理 |

派发规则与正文一致：规划器输出**不再叠加清理**（§E.1），待输入插入才补清理段。

### 三个「看起来该这么做，其实不行」的点

**① 事后扫字符串清理不成立。** 想过写一个 `cleanupDelimitersInText(text)`
把 `****`、`**A****B**` 扫掉，实测行不通：这些残留在 Lezer 里**根本不是合法的强调节点**，
解析器事后找不回它们，`collectAllMarkRegions` 返回空、C3 无从下手。
空定界符对必须在**产生它的地方**堵住 —— `serializeInlineStyledElement` 内容为空时整对丢弃。

**② 渲染快照必须能失效。** `data-mda-inline-source` 存的是渲染那一刻的源码（`**加粗**`），
而 `textContent` 是可见文字（`加粗`）。序列化时若无条件吐回快照，
用户在段内改的字会被**整个吞掉**（改成 `加粗改了` 仍写回 `**加粗**`，删空则文字复活）。
因此渲染时同时写 `data-mda-inline-text`（可见文字），
序列化只有两者一致才认快照，否则按 class + 当前文字重建。

**③ 格内快捷键不走 `runFormatCommand`。** `table-chrome.js` 的 cell `keydown`
自己拦了 Ctrl+B/I/U/`` ` ``/Shift+X 并 `stopPropagation`，**根本到不了** `tryWidgetFormatCommand`，
所以后者里的 collapsed 判断形同虚设。「无选区只改后续输入格式」必须在 chrome 的 keydown 里
再做一遍（`isCellSelectionCollapsed` → `toggleWidgetPendingMark`）；
否则会落到 `assist.toggleWrap` 的空选区分支，往格里写入 `**<零宽空格>**`。
排查时若只看 `format-commands.js` 会得出完全错误的结论 —— 先确认命令的实际入口。

### 格内编辑不经 CM6 事务，三处须显式 flush

格内改动只落在 widget 的 DOM 上，文档既不脏也拿不到新内容，于是：

- `mutate(fn)` 的 `syncFromDomIfNeeded()` 必须在 `mutating = true` **之前**调用
  （该函数自身以 `mutating` 早退），否则加行/列基于旧 `parsed` 重建，正在编辑的格子内容丢失；
- `saveFile` / `tryAutosave` 的 flush 必须在 `if (!dirty) return` **之前**，否则保存被整个跳过；
- `handleAppCloseRequest` 同理先 flush 再判脏，否则「改了格子就关窗」会被当成没改过。

flush 本身还有个副作用：写回文档会让 widget 重建，正在编辑的 `td` 随之销毁、焦点掉回 body。
Ctrl+S 是编辑途中的高频动作，被踢出格子很难接受，所以 `flushAllTableWidgets`
先 `captureFocusedCellPos`（块序号/行/列 + 可见偏移）、写回后 `restoreFocusedCellPos` 落回去。

### 工具栏选中态：换数据源，还得自己找刷新时机

同一个原因（格内选区不在 CM6 文档里）也让工具栏失灵：`getInlineToolbarState(view.state)`
读的是停在表首的文档选区，点进格内加粗文字按钮**一律不亮**。三处接线：

| 问题 | 做法 |
|------|------|
| 状态取不到 | `kind === 'table-cell'` 时改问 `getCellInlineState(cell, target)` —— 单元格 Markdown + 可见偏移 → `inlineStateInText` |
| 移光标不刷新 | 听 document `selectionchange`（rAF 合并，限 `focusInWidgetInlineEditable()`）；格内移光标不产生 CM6 事务 |
| 按键武装不刷新 | `setWidgetPendingListener` 回调 —— Ctrl+B 连选区都不改，`selectionchange` 也不会来 |

待输入格式的基准必须取光标处已有标记（`getCellInlineFlags`），否则「在斜体里按 Ctrl+B」
会把斜体一并关掉；`syncWidgetPendingForCaret` 对齐正文 `pendingFormatField` 的 selMove 分支，
光标移到标记上下文不同处即丢弃覆盖态，避免跨落点串味。

两个容易写错断言的点：

- **段头/段尾本就报「已加粗」**。`markCoverage` 折叠位会同时 `resolveInner(pos, 1)` 和 `(pos, -1)`，
  紧邻定界符的位置算在样式内 —— 这正与「在那里输入会融合进该段」一致。
  所以段头按 Ctrl+B 的语义是**取消**（得到 `X**加粗**`），不是再包一层。
- **取消样式后要能真的取消**。`onWidgetBeforeInput` 旧守卫见 `marks` 全关就放行，
  浏览器把字插进 `<strong>` 里，序列化回来还是 `**...**`（取消不掉）。
  现在「marks 全关但光标在样式段内」也接管，交 `planTypedInsertInText` 拆分。

还有一条隐蔽的：`table-chrome.js` 的 `onDocPointer`（document mousedown 捕获）
把工具栏点击当成「点到表外」，`clearTableInteraction` 会 blur 单元格并 `removeAllRanges`，
于是**无选区时点加粗光标直接没了**。有选区那条路看着正常，只是碰巧被
`applyInlineFormatToTableCell` 末尾的 `restore()` 救了回来 —— 同一个缺陷被掩盖了一半，
排查时容易误判成「只有无选区才有问题」。修法是放行 `.mda-cm-edit-toolbar` 内的点击。

回归见 `tests/e2e/gui/table-cell-edit.spec.ts`（加行/加列不丢内容、段内改字不被快照吞掉、
段头 Ctrl+B 是取消、部分取消拆分、无选区不写空对、工具栏高亮与格外一致、保存不踢光标）与
`tests/gui/editor/inline-string-ops.test.ts`、`table-cell-serialize.test.ts`。

### 格内输入：IME 走 composition，普通键入按「规划 ≠ 朴素插入」才接管

格内 `beforeinput` 拦截曾把**组字第一击**当成正式输入：那一击的 `data` 是拼音首字母 `c`，
`isComposing` 为真。接管后写回并重建单元格 DOM，组字被打断，剩下的拼音丢失、上屏的汉字
另起一处，结果是 `**加**c测试**粗**`。所以：

| 事件 | 做法 |
|------|------|
| `beforeinput` 且 `isComposing` / `insertCompositionText` | **放行**，一律交给 composition 路径 |
| `compositionstart` | 拍下**组字前**的干净取材：单元格 Markdown、光标 md 偏移、意图标记 |
| `compositionend` | 用 `e.data` 在该快照上跑 `planTypedInsertInText`，整体写回 |

这与 D1/D2 的「干净文档」是同一条原则，只是格内没有 CM6 文档可 `state.update` 摘除待删区，
干净文档改由 compositionstart 的快照提供。

另一半是**未武装待输入时的落点**：光标停在样式段头前时 `getCellInlineFlags` 会报「在样式内」
（`resolveInner` 双向，与正文一致），但浏览器的默认插入落在 span **外**，得到 `测试**加粗**`，
与正文的 `**测试加粗**` 不一致。故取材时 `marks` 在未武装时回退成格内光标处的标记，
让规划器决定落点。为免每次按键都重建单元格 DOM，未武装时只在
**规划结果 ≠ 在同一 md 偏移做朴素插入**时才 `preventDefault` 接管（段中输入两者一致，直接放行）；
武装态一律接管。**武装态插入后须保留 `widgetPending`**（`applyCellPlannedInsert`）：
只清 pending 会导致第二个字又按落点周围样式融合、工具栏弹回选中（`a**bc加粗**`）。
诊断开 `mda-editor-debug-inline-format`，看 `cell.typedInsert` 的
`md` / `mdPos` / `marks` / `takeover`。

格内完整验证矩阵在 `tests/e2e/gui/table-cell-inline-matrix.spec.ts`：五种标记 × 头前/文中/末尾，
覆盖输入法中文、工具栏一次点击切换、取消后输入、四向拖选删除、部分取消拆分、连续操作串味、右键。

## E. 易踩的坑

1. **规划器输出不要再过清理**：C1/C2 会重写定界符，若再对同一批区段跑 C3，
   映射后的旧坐标会把新写入的定界符当成「残余」删掉，轻则少一对定界符、重则清空整行。
   所以派发分成 `dispatchPlannedChange`（不清理）与 `dispatchWithDelimiterCleanup`（清理）两条。
2. **清理事务必须 `sequential: true`**：第二段变更的坐标基于第一段之后的文档。
3. **区段映射的结合性**：`open` 用 `(from,-1)/(to,-1)`、`close` 用 `(from,1)/(to,1)`，
   否则紧贴定界符的插入会被算进定界符内部，长度校验误判。
4. **按行窗口取材**：`collectMarkRegions` / `collectDelimiterRuns` 只扫当前行范围，
   长文档下每次按键全树遍历会明显掉帧。
5. **选区删除要保留半覆盖的定界符对**：先 `snapOutOfDelimiters` 把端点推出定界符内部，
   再走 `planDeleteRangePreservingPairs`（§C3b）。**不要**改成「撑到整对」——
   那会连带删掉用户没选中的可见文字。
6. **清理只判「结构完好」的区段**：定界符长度变了就说明本次变更自己重写了它，
   必须跳过。这条一旦漏掉，规划再正确也会被清理毁掉（见 §C3）。
7. **改完要走全链路验证**：只测规划函数会漏掉「规划正确但清理毁掉」这类组合缺陷。
   `tests/gui/editor/inline-input-sweep.test.ts` 按
   五类标记 × 五个落点 × 延续/取消 × 键盘/IME/IME拼音 扫 300 例，并比对三种模式结果一致。
8. **验收前确认跑的是新代码**：CM6 编辑器是打包产物 `dist/gui/renderer/editor.bundle.js`，
   改 `src/gui/renderer/editor/**` 后必须 `npm run build`（含 `build:editor`）。
   更隐蔽的是 `main.js` 的**单实例锁**：已开着 MDA 时再 `npm run gui`，新进程会直接退出、
   只把旧窗口激活——看起来重启了，其实还在跑旧代码。须先关掉所有窗口，或 `Ctrl+R` 重载。
   模型层测不出的运行时问题用 `tests/e2e/gui/ime-inline.spec.ts`（真实 Electron +
   CDP `Input.imeSetComposition` 模拟输入法），它同样需要独立 `--user-data-dir`。
9. **e2e 必须模拟「同一行上连续操作」**：每个用例都开新文档会漏掉**跨操作的状态残留**。
   实测缺陷：pending 格式在上一段编辑里被自动武装成 `code`，撤销不改选区所以没清，
   下一次点进下划线段落时被 `keepOverride` 带过来，输入直接插出 `` ` `` 而不是 `~`。
   因此 `pendingFormatField` 只对**用户在工具栏显式切换**（`explicit: true`）的覆盖态
   做跨光标移动保留；由 selMove / 输入自动武装的一律按新位置的样式重新武装。
   回归用例见 `tests/e2e/gui/inline-delimiter-edit.spec.ts`（连续插入 + 四向拖选删除）。
10. **模拟输入法要送拼音，不要送汉字**：组字阶段进文档的是拼音字母，上屏才换成汉字。
    直接把最终汉字当组字文本，会让 `findCommittedText` 命中、走进 `planCompositionEndReplace`，
    从而绕开真正出问题的替换路径（见 §D2）——这正是「单测 e2e 全绿但用户一打字就坏」的成因。
    定位这类问题最快的手段是打开内置日志：
    `localStorage.setItem('mda-editor-debug-inline-format','1')`（`readFlag` 每次实时读取，
    无需 reload），`input.check` / `buildInsert` 的 `docSnap` 会直接暴露取材文档是否被污染。
