# {project_name} 开发工作流 — 阶段化开发流程

> **适用范围**：任意软件工程任务 —— 新建项目、既有项目迭代、缺陷修复、性能优化、重构与架构迁移、探索性原型。
> 不绑定语言 / 框架 / 交付形态；命题式任务（如 L2 考核）只是其中一类实例。
> **状态**：模板（从 MDA 蒸馏并广泛化）。使用前按两个维度裁剪：
> ① **按项目类型**裁目录与约束（见 skill 的 `references/cropping-guide.md`）；
> ② **按任务规模**裁阶段与文档（见下方「任务分档与阶段裁剪」）。

---

## 流程总览

```
P0-需求分析 → P1-架构设计 → P2-详细设计 → P3-实现步骤 → P4-实现
   ↓确认        ↓确认         ↓确认         ↓确认          ↓循环
  git commit   git commit    git commit    git commit     git commit
```

每阶段产出文档到 `docs/`，用户确认后 git commit，进入下一阶段。
**阶段可按任务规模裁剪，门禁不可裁剪。**

## 适用范围与阶段裁剪

### 1. 项目适配层（接入项目时先填这张表）

本工作流规定「做什么、在哪设门禁」，不规定「用什么工具做」。
在 `AGENTS.md` 中声明下列等价动作，流程各处出现的通用动作即按此解释：

| 通用动作 | 本项目等价命令 / 方式 |
|---------|---------------------|
| 构建 | `{build}` |
| 静态 / 类型检查 | `{typecheck}` |
| 单元测试 | `{unit_test}` |
| 集成 / 端到端 | `{e2e_test}` |
| 人工 / 实机验证 | `{manual_verify}`（无 UI 项目可标「不适用」） |
| 交付物校验 | `{release_check}` |
| 不变量校验 | `{invariant_check}`（项目级正确性红线：数据不丢 / 幂等 / 向后兼容等；无则写「无」） |

标注「不适用」的动作可跳过，但**不得**因此顺带跳过同层级的其他校验。

### 2. 任务分档与阶段裁剪

按「影响面 + 不可逆程度」定档：

| 档位 | 触发判据（满足任一即升档） | P0 | P1 | P2 | P3 | P4 | 最小产出物 |
|------|--------------------------|----|----|----|----|----|-----------|
| **T0 微改** | 单文件、无行为变化（文案 / i18n / 注释 / 格式） | – | – | – | – | ✅ | 规范的 commit message |
| **T1 缺陷修复** | 现象明确、不改公共接口、改动收敛在已有模块 | 合并为「根因说明」段落 | – | – | – | ✅ | 根因 + 修复 + **回归用例** |
| **T2 小增强** | 单模块、接口向后兼容、无数据格式变更 | 精简版（目标 / AC / 不做清单） | 合并入 P0 | 精简版（算法 + 边界表） | 合并入 P2 | ✅ | 一份合并设计文档 |
| **T3 模块级特性** | 跨 ≥2 模块，或新增公共接口 / 配置项 | ✅ | ✅ | ✅ | ✅ | ✅ | 四份阶段文档 |
| **T4 子系统 / 架构迁移** | 新进程 / 新依赖 / 数据格式变更 / 迁移不可逆 | ✅ + 干系人确认 | ✅ ≥3 方案 + 必要时 POC | ✅ | ✅ 分里程碑 + 回滚 | ✅ 逐里程碑验收 | 四份文档 + 里程碑验收清单 |
| **T5 探索原型** | 需求不明确或技术可行性未知 | 问题陈述 + 成功判据 | POC 方案 | – | – | 原型（**不并入主干**） | POC 结论报告 |

补充规则：
- **T5 是前置档不是终点**：POC 有结论后回到 T2/T3/T4 重新定档再进主干。
- **档位只升不降**：施工中发现跨模块或接口变更，立即升档补文档；确需降档须用户确认。
- 不确定档位时**就高不就低**。

### 3. 不可裁剪的门禁（任何档位都适用）

1. **方案确认门** —— 非平凡改动实施前先给方案并获用户同意。
2. **输出校验三层** —— 结构/类型、语义不变量、行为验证，每层至少一项。
3. **人工验证门** —— 涉及 UI / 交互 / 视觉呈现的改动须实机确认（无 UI 项目不适用）。
4. **沉淀门** —— 本轮新坑当轮写入 `AGENTS.md` 隐性规范或 few-shot 正反例。
5. **提交规范** —— Conventional Commits，小粒度原子提交。
6. **需求不明确不得直接进 P4** —— 先走 T5 探索档。

## 通用迭代协议（六步循环）

所有工作阶段（P0-P4）严格遵循以下 6 步流程。
每一步「用什么推理手段执行」见下方「推理侧工程组合」。

### Step 1 — 审查（Review）

开始修改/产出前，先审查与任务相关的现有状态，识别潜在风险和改进点。

**P0-P3（设计阶段）**：
- 阅读上一阶段产出 + 用户反馈
- 检查模板要求与当前产出的差距
- 识别需求文档中未覆盖但有影响的细节

**P4（实现阶段）**：
- 阅读 P2/P3 中当前任务的详细设计/伪代码/接口规格
- 检查当前代码状态（`git status`, `git log`）
- 确认无未提交的脏改动

**产出**：结构化的审查结论（问题列表 + 风险 + 改进建议）。

### Step 2 — 实施（Implement）

基于需求和审查结论进行产出。

**P0-P3**：对照模板撰写设计文档，覆盖全部内容要点。
**P4**：编写代码，严格遵循 P2 的伪代码/算法/接口规格。

**重要**：
- **P0-P3**：产出后呈现给用户确认
- **P4**：非平凡改动须先向用户确认方案，获同意后再动手

### Step 3 — 自查（Self-Review）

**P0-P3**：
- 对照模板 checklist 逐项检查（Spec Self-Review 6 项）
- 检查内部一致性（前后章节结论不矛盾）
- 检查无占位符（TODO/TBD/待定）

**P4**：
- 代码可编译/可运行（按项目：`tsc --noEmit` / `npm run build` / 等）
- 对照 P2 算法伪代码检查逻辑
- review diff（`git diff`）确认只改了预期文件

### Step 4 — 验证（Verify）

**P0-P3**：
- 对抗自检：反向追问设计中的推测和假设
- 预死亡分析：假设方案失败，最可能的原因
- 用户确认

**P4**：
- 运行测试套件，全部通过
- 核心功能手动验证
- 边界/异常场景不崩溃
- 输出格式符合规范（如 CLI：stdout 仅数据，stderr 走日志）

> **【可选硬约束】UI 层改动须人工测试**
> 若项目含 GUI / Web 前端 / Desktop 壳，自动化测试与 build 通过 **不等于** 验证完成。须：
> 1. 启动应用并请用户实机操作确认本次改动点；
> 2. 在用户明确回复「测试通过」前，**不得**提交或推进下一功能；
> 3. 问题未闭环则回到 Step 1。
>
> 在 `quality.md` §5 登记具体审核点；无 UI 的项目可删除本约束。

### Step 5 — 文档（Document）

**P0-P3**：产出即为文档，用户确认后即完成。

**P4 — 通用清单**（按改动范围勾选）：

| 文档 | 何时更新 |
|------|----------|
| `README.md` | 接口/配置/使用方式/功能变更；测试数或覆盖率变化 |
| `AGENTS.md` | 架构/接口/禁止事项/隐性规范/关键文件索引变更 |
| `quality.md` | 测试数、覆盖率、人工审核点、校验链路变更 |
| `docs/few-shot-examples.md` | 新增易错点需沉淀 ✅/❌ 正反例 |
| `docs/prompts/` | 每轮 AI 协作 prompt 与动作记录（L2 要求 ≥3 轮） |
| `docs/P1–P2` | 架构/设计有调整时 |
| `tests/` | 核心逻辑变更须同步用例 |
| `samples/` | 新增演示场景时 |

**P4 — UI 层附加清单**（`src/gui/**` 或前端目录有变更时）：

1. `AGENTS.md` 同步新 API 与隐性规范
2. `quality.md` §5 补充实机验证要点
3. 可复现陷阱写入 `docs/few-shot-examples.md`
4. 对照 `docs/screenshots/README.md` 提示用户补截图/录屏
5. 同步 README / `quality.md` 中的测试数与覆盖率

> **【可选硬约束】UI 截图/录屏不由 AI 伪造**
> GUI 功能变更且用户确认实机通过后，Step 5 须输出「待补截图清单」。

### Step 5.5 — 提交（Commit）

- 设计阶段：`P0:` / `P1:` / `P2:` / `P3:` 前缀
- 实现阶段：`<type>(<scope>): <description>`（feat/fix/refactor/test/docs/chore）
- 小粒度提交，不积攒多阶段变更

### Step 6 — 下一步（Next）

- 对照阶段规划确认下一阶段/任务
- 遗留问题标注优先级（P0 阻塞 / P1 重要 / P2 后续）
- 启动下一轮 Step 1

## 推理侧工程组合（Inference Stack）

> 六步循环规定「做什么」，本节规定「用什么推理手段做」。
> 按任务档位启用，不要求每轮全开 —— 手段本身有 token 与时间成本。

### 1. 八件手段与落地方式

| 手段 | 落地方式 | 何时必用 | 边界 / 成本约束 |
|------|---------|---------|----------------|
| **Prompt·思维链** | 阶段模板的对抗自检 / 预死亡分析；P2 伪代码先行；疑难 bug 先写「根因假设 → 证伪路径 → 预期观测」再动手 | T2 以上；任何「现象与代码不符」的排查 | 机械改动不强制展开推理链 |
| **Prompt·少样本** | `docs/few-shot-examples.md` 的 ✅/❌ 成对示例；`AGENTS.md` 隐性规范即负例库（作为常驻规则自动注入） | 触碰已沉淀过陷阱的领域 | 踩新坑**必须当轮回沉淀**，否则同类问题会重犯 |
| **RAG·私域检索** | 固定检索链：`AGENTS.md` 关键文件索引 → `docs/` 设计文档与协作记录 → 全仓代码检索 → 历史会话 | 动手前一律先检索，禁止凭记忆断言代码行为 | 先查索引再全仓搜；外部检索仅用于第三方库 API 与版本问题，结论须落到版本号 |
| **工具调用** | ① 校验类：`{typecheck}` / `{unit_test}` / `{e2e_test}` / `{release_check}`；② 代码解释器等价物：一次性脚本直接加载产物跑闭环；③ 自建诊断探针：调试开关 + 关键中间量快照（见 P2 模板「可观测性与诊断」） | 凡涉及「解析结果 / 坐标 / 状态是否成立」的判断 | 用真实运行结果回答，**不靠推测**；临时脚本用完即删 |
| **任务分解 Agent** | 三层：跨会话用 P3 任务 DAG；会话内 3+ 步用 todo 清单；只读勘察外包给探索型子代理 | T4 必须先出 DAG；跨模块链路排查优先并行勘察 | **写操作不并行外包**（同文件并行写易产生偏移/覆盖事故）；子代理只带回结论，落手改动由主 agent 执行，避免隐性规范丢失 |
| **多模型路由** | 推理密集（根因定位 / 架构 / 核心算法）→ 强推理模型高思考档；机械批量（补键、样板测试、重命名）→ 快模型；异构第二意见 → 独立 review 子代理 | 出现大量重复机械改动，或需要独立视角复核时 | 触碰 `AGENTS.md` 禁止事项与项目红线链路的改动**不得下放给快模型** |
| **输出校验** | 三层递进：① 结构/类型 —— `{typecheck}` + 入口枚举/参数守卫；② 语义不变量 —— `{invariant_check}` 与关键断言；③ 行为 —— `{unit_test}` + `{e2e_test}` + `{manual_verify}` | 每轮 Step 3/4 全部执行 | **自动化全绿 ≠ 通过**：UI 改动仍受人工验证门约束；模型的规划结论必须过真实运行校验，不接受自证 |
| **自我反思** | Step 3 自查 + Step 4 对抗自检 / 预死亡；每轮根因→修复→遗留写入 `docs/prompts/`；可另用评审规则做 LLM-as-judge 自评 | 每轮必做；用户反馈「仍有问题」时强制重走 | **改口必须附工具证据**（诊断输出 / 测试结果 / diff），不接受「再想了想应该是」 |
| **多结果投票 / 交叉校验** | ① 路径级：对同一语义的多条实现路径（如键盘输入 / 输入法 / 粘贴）做参数化扫掠并**比对结果一致**；② 方案级：在隔离工作树跑 N 版实现 | 高风险算法分歧且验证成本低于返工成本 | 择优准则固定为「过校验 + 过端到端 + diff 最小」；**投票不替代根因定位**，多数票可能一起错 |

### 2. 与六步循环的对应

| Step | 必用 | 按需 |
|------|------|------|
| 1 审查 | RAG 检索链；`git status` / `git log` | 子代理并行勘察 |
| 2 实施 | 少样本对照隐性规范；非平凡改动先出方案 | 任务分解；机械批量走快模型 |
| 3 自查 | 思维链复核算法一致性；`{typecheck}`；`git diff` 只改预期文件 | 诊断探针核对中间量 |
| 4 验证 | 三层输出校验 + 对抗自检；**UI 实机确认** | 多结果投票；第二意见 review |
| 5 文档 | 反思沉淀：`AGENTS.md` / few-shot / `docs/prompts/` | `quality.md`、截图清单 |
| 6 下一步 | 遗留项按 P0/P1/P2 标注 | 确认是否换档 |

### 3. 按档位开哪几件

| 档位 | 手段组合 | 完成判据 |
|------|---------|---------|
| **T0/T1** | 少样本 + RAG 索引 + `{typecheck}` + 回归用例 | 回归用例锁定现象 |
| **T2** | 上述 + 思维链根因假设 + 单测/集成 | 校验三层各至少一项 |
| **T3** | 上述 + 诊断探针 + 端到端 + 自我反思 + UI 实机 | 自动化双过 + 用户确认 |
| **T4** | 上述 + 任务分解 DAG + 阶段门 + 多结果投票 | 阶段文档确认后才开工实现 |

### 4. 推理侧硬性约束

1. **不以记忆代替检索** —— 断言代码行为前必须有工具输出支撑；文档与代码冲突时以代码为准并回头修文档。
2. **不以「全绿」代替实机** —— UI 改动未获用户确认不得提交或推进。
3. **不并行写同一文件** —— 同文件多处写操作一律串行。
4. **结论改口须附证据** —— 推翻先前判断时同时给出工具证据。
5. **投票不替代根因** —— 多数一致只是信号。
6. **每轮踩坑必沉淀** —— 否则视为本轮未完成。

## 阶段规划

> 以下为 **T3 完整档**的阶段定义；T0–T2 按裁剪矩阵合并或跳过，T4 增加干系人确认与里程碑验收。
> 各阶段模板自带「模板元信息」（版本 / 适用档位 / 裁剪指引）与「退出门禁」，按档位填写对应小节。

### P0 — 需求分析

**输入**：需求文档 / 命题说明  
**输出**：`docs/P0-requirements.md`  
**模板**：`docs/templates/requirement.template.md`

| Step | 做什么 |
|------|--------|
| 1 审查 | 精读需求，提取显式要求 + 隐式约束 |
| 2 实施 | 背景/目标/功能/用户故事/AC(Given-When-Then)/非功能/接口契约/假设/风险 |
| 3 自查 | Spec Self-Review 6 项；AC 必须 G/W/T 格式 |
| 4 验证 | 对抗自检 3 问；提交用户确认 |
| 5.5 commit | `P0: 需求分析文档 — {主题}` |

### P1 — 架构设计

**输入**：P0  
**输出**：`docs/P1-architecture.md`  
**模板**：`docs/templates/design.template.md`

| Step | 做什么 |
|------|--------|
| 2 实施 | 预调研→方案对比(≥3)→推荐方案(Mermaid/模块影响/任务初稿) |
| 3 自查 | Mermaid ≤12 节点；假设标注证据+置信度 |
| 4 验证 | 对抗审查 4 问；综合置信度 ≥80% |
| 5.5 commit | `P1: 架构设计 — {摘要}` |

### P2 — 详细设计

**输入**：P1  
**输出**：`docs/P2-detailed-design.md`  
**模板**：`docs/templates/detailed-design.template.md`

| Step | 做什么 |
|------|--------|
| 2 实施 | 核心算法(伪代码+状态机+边界表)、策略设计、CLI/GUI 规格、边界用例 E1-EN、测试设计 |
| 3 自查 | 伪代码可直译；边界表覆盖 P0 全部 AC |
| 5.5 commit | `P2: 详细设计 — {摘要}` |

### P3 — 实现步骤

**输入**：P2  
**输出**：`docs/P3-implementation-plan.md`  
**模板**：`docs/templates/dev-plan.template.md`

| Step | 做什么 |
|------|--------|
| 2 实施 | 接口定义、Mermaid 架构图、任务 DAG、预死亡分析、回滚策略 |
| 3 自查 | 任务 2-5 分钟粒度；依赖无环 |
| 5.5 commit | `P3: 实现步骤规划 — {N} 阶段 {M} 任务` |

### P4 — 实现

**输入**：P3  
**输出**：代码 + 测试 + 分阶段 commit

| Step | 做什么 |
|------|--------|
| 1 审查 | 读 P2/P3 当前任务；`git status` 确认干净 |
| 2 实施 | 严格遵循 P2 规格 |
| 3 自查 | 编译 + diff review |
| 4 验证 | 测试全绿 + 手动验证 + UI 实机（如有） |
| 5 文档 | 通用清单 + UI 附加清单 |
| 5.5 commit | `feat(scope): ...` 等 |

### P4 实现顺序（按项目填写）

在 P3 完成后，将 DAG 归纳为 Phase 列表，示例：

```
Phase A: 项目脚手架
Phase B: {core_module} — 按依赖顺序
Phase C: {adapter_layer} — CLI / API / 等
Phase D: {ui_layer} — 如有
Phase E: 测试 — 边界用例 + 集成
Phase F: 交付 — README / samples / 截图 / AI 协作记录
```

### P4 关键原则

1. **先编译通过，再跑测试**
2. **核心先行** — 业务逻辑验证通过后再做适配层/UI
3. **问题即修复** — 测试失败当场修复，不积压
4. **源文件/数据安全** — 按 P2 定义的写入策略执行（原子写入、校验等）
