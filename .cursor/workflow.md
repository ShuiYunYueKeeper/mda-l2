# 阶段化开发工作流

> **适用范围**：任意软件工程任务 —— 新建项目、既有项目迭代、缺陷修复、性能优化、重构与架构迁移、探索性原型。
> 不绑定语言 / 框架 / 交付形态；命题式任务（如 L2 考核）只是其中一类实例。
> 与技术栈相关的具体命令不写死在流程里，由各项目在「项目适配层」声明。
> **状态**：已在 MDA（Markdown 工作台，TypeScript + CLI + Electron + MCP）跨 8 个里程碑完整验证。

---

## 流程总览

```
P0-需求分析 → P1-架构设计 → P2-详细设计 → P3-实现步骤 → P4-实现
   ↓确认        ↓确认         ↓确认         ↓确认          ↓循环
  git commit   git commit    git commit    git commit     git commit
```

每阶段产出文档到 `docs/`，用户确认后 git commit，进入下一阶段。
**阶段可按任务规模裁剪，门禁不可裁剪** —— 裁剪规则见下一节。

---

## 适用范围与阶段裁剪

### 1. 项目适配层（接入新项目时先填这张表）

本工作流规定「做什么、在哪设门禁」，不规定「用什么工具做」。
新项目接入时在 `AGENTS.md` 中声明下列等价动作，流程各处出现的通用动作即按此解释：

| 通用动作 | 本项目等价命令 / 方式 | MDA 实例（参考） |
|---------|---------------------|-----------------|
| 构建 | `{build}` | `npm run build` |
| 静态 / 类型检查 | `{typecheck}` | `tsc --noEmit` |
| 单元测试 | `{unit_test}` | `npm test`（jest + 覆盖率） |
| 集成 / 端到端 | `{e2e_test}` | `npx playwright test` |
| 人工 / 实机验证 | `{manual_verify}` | 启动 GUI 由用户实机确认 |
| 交付物校验 | `{release_check}` | `node scripts/verify-release.js` |
| 不变量校验（如有） | `{invariant_check}` | `verifySourceProtection`（正文逐字节不变） |

规则：
- 某动作在本项目**确实不适用**（如纯 CLI 项目无「实机 UI 验证」）时可标注「不适用」，
  但**不得**因此顺带跳过同层级的其他校验（见「输出校验三层」）。
- **不变量校验**是项目特有的正确性红线（数据不丢、正文不改、幂等、向后兼容等），
  没有则显式写「无」，有则必须进 CI 或进 Step 4 清单。

### 2. 任务分档与阶段裁剪

按「影响面 + 不可逆程度」定档，决定跑几个阶段、产出几份文档：

| 档位 | 触发判据（满足任一即升档） | P0 | P1 | P2 | P3 | P4 | 最小产出物 |
|------|--------------------------|----|----|----|----|----|-----------|
| **T0 微改** | 单文件、无行为变化（文案 / i18n / 注释 / 格式） | – | – | – | – | ✅ | 规范的 commit message |
| **T1 缺陷修复** | 现象明确、不改公共接口、改动收敛在已有模块 | 合并为「根因说明」段落 | – | – | – | ✅ | 根因 + 修复 + **回归用例**；坑写入协作记录 |
| **T2 小增强** | 单模块、接口向后兼容、无数据格式变更 | 精简版（目标 / AC / 不做清单） | 合并入 P0 | 精简版（算法 + 边界表） | 合并入 P2 | ✅ | 一份合并设计文档 |
| **T3 模块级特性** | 跨 ≥2 模块，或新增公共接口 / 配置项 | ✅ | ✅ | ✅ | ✅ | ✅ | 四份阶段文档 |
| **T4 子系统 / 架构迁移** | 新进程 / 新依赖 / 数据格式变更 / 迁移不可逆 / 影响交付形态 | ✅ + 干系人确认 | ✅ ≥3 方案 + 必要时 POC | ✅ | ✅ 分里程碑 + 回滚 | ✅ 逐里程碑验收 | 四份文档 + 里程碑验收清单 |
| **T5 探索原型** | 需求不明确或技术可行性未知 | 问题陈述 + 成功判据 | POC 方案 | – | – | 原型（**不并入主干**） | POC 结论报告 |

补充规则：
- **T5 是前置档不是终点**：POC 得出结论后，必须回到 T2/T3/T4 重新定档再进主干。
- **档位只升不降**：施工中发现跨模块或接口变更，立即升档并补齐该档文档，
  不得在低档里硬做完；确需降档须说明理由并经用户确认。
- 不确定档位时**就高不就低**。

### 3. 不可裁剪的门禁（任何档位都适用）

1. **方案确认门** —— 非平凡改动实施前先给方案并获用户同意（T0/T1 可在动手后同轮说明）。
2. **输出校验三层** —— 结构/类型、语义不变量、行为验证，每层至少一项（详见「推理侧工程组合」§1）。
3. **人工验证门** —— 凡涉及 UI / 交互 / 视觉呈现的改动，自动化通过 ≠ 验证完成，须用户实机确认。
4. **沉淀门** —— 本轮踩到的新坑当轮写入 `AGENTS.md` 隐性规范或 few-shot 正反例。
5. **提交规范** —— Conventional Commits，小粒度原子提交，不跨阶段积攒。
6. **需求不明确不得直接进 P4** —— 先走 T5 探索档，禁止边猜边写。

## 通用迭代协议（六步循环）

所有工作阶段（P0-P4）严格遵循以下 6 步流程。
每一步「用什么推理手段执行」（思维链 / 少样本 / RAG 检索 / 工具与探针 / 任务分解 / 模型路由 / 输出校验 / 自我反思 / 多结果投票）见下方「推理侧工程组合」。

### Step 1 — 审查（Review）

开始修改/产出前，先审查与任务相关的现有状态，识别潜在风险和改进点。

**P0-P3（设计阶段）**：
- 阅读上一阶段产出 + 用户反馈
- 检查模板要求与当前产出的差距
- 识别需求文档中未覆盖但有影响的细节
**P4（实现阶段）**：
- 阅读 P2/P3 中当前任务的详细设计/伪代码/接口规格
- 检查当前代码状态（`git status`, `git log`）
- 确认无未提交的脏改动

**产出**：结构化的审查结论（问题列表 + 风险 + 改进建议），口头或写入文档。

### Step 2 — 实施（Implement）

基于需求和审查结论进行产出。

**P0-P3（设计阶段）**：对照模板撰写设计文档，覆盖全部内容要点。
**P4（实现阶段）**：编写代码，严格遵循 P2 的伪代码/算法/接口规格。

**重要**：
- **P0-P3**：产出后呈现给用户确认
- **P4**：实施前需向用户确认方案（非平凡改动时），获得同意后再动手

### Step 3 — 自查（Self-Review）

完成产出后立即进行自我审查。

**P0-P3（设计阶段）**：
- 对照模板 checklist 逐项检查（如 Spec Self-Review 6 项）
- 检查内部一致性（前后章节结论不矛盾）
- 检查无占位符（TODO/TBD/待定）
**P4（实现阶段）**：
- 代码可编译/可运行（`tsc --noEmit` / `npm run build`）
- 检查逻辑正确性（对照 P2 算法伪代码）
- 检查与设计文档的一致性
- review diff（`git diff`）确认只改了预期的文件

### Step 4 — 验证（Verify）

验证当前阶段的正确性和完整性。

**P0-P3（设计阶段）**：
- 对抗自检：反向追问设计中的推测和假设
- 预死亡分析：假设方案失败，最可能的原因
- 用户确认
**P4（实现阶段）**：
- 运行测试套件（`npm test` / `jest --coverage`），全部通过
- 核心功能手动验证（CLI 命令执行 + GUI 交互）
- 边界/异常场景不崩溃（E1-E25）
- CLI 输出格式符合规范（stdout 仅数据，stderr 走日志）
- 如需用户配合验证（如 GUI 截图），主动说明

> **【硬性约束】GUI 改动必须人工测试通过后才能继续**
> 凡涉及 GUI（`src/gui/**`：main/preload/renderer）的修改，自动化测试与 `npm run build` 通过 **不等于** 验证完成。必须：
> 1. 启动 GUI（`npm run gui -- <file>`）并请用户实机操作复现/确认本次改动点；
> 2. 在用户明确回复「测试通过 / 已修复」之前，**不得**提交，也**不得**推进到下一阶段或下一个功能；
> 3. 若用户反馈仍有问题，回到 Step 1 修复后重新走人工测试，直至通过。

### Step 5 — 文档（Document）

更新相关文档，保持代码与文档同步。

**P0-P3**：产出即为文档本身，用户确认后即完成。

**P4 — 通用清单**（按改动范围勾选，无关项跳过）：

| 文档 | 何时更新 |
|------|----------|
| `README.md` | 接口/配置/使用方式/GUI 功能变更；覆盖率或测试数变化 |
| `AGENTS.md` | 架构/接口/禁止事项/隐性规范/关键文件索引变更 |
| `quality.md` | 测试数、覆盖率、人工审核点、校验链路变更 |
| `docs/few-shot-examples.md` | 新增易错点或 GUI 交互陷阱需沉淀 ✅/❌ 正反例 |
| `docs/prompts/` | 每轮 AI 协作 prompt 与动作记录（命题式交付另有 ≥3 轮的硬性要求） |
| `docs/P1–P2` | 架构/设计有调整时 |
| `tests/` | 核心逻辑变更须同步用例 |
| `samples/` | 新增演示场景时 |

**P4 — GUI 改动附加清单**（`src/gui/**` 有变更时**必须**执行）：

1. **协作指南**：`AGENTS.md` 同步新 API（preload 桥接）、隐性规范（如 4d–4g）。
2. **质量专章**：`quality.md` §5 人工审核点 — 补充本次 GUI 交互的实机验证要点。
3. **Few-shot**：若出现可复现陷阱（如坏批注泄漏、缩放模糊、dirty 冲突），在 `docs/few-shot-examples.md` 增 ✅/❌ 成对示例。
4. **截图 / 录屏（须提示用户）**：
   - 对照 `docs/screenshots/README.md`「待补充素材」表，列出本次变更涉及的**建议文件名 + 拍摄要点**；
   - **在 Step 5 向用户明确发出补充请求**（AI 不能代替实机截图/录屏）；
   - 用户补充素材后，更新 `README.md`「界面截图与演示」引用（可单独 `docs:` commit）。
5. **覆盖率**：`npm test` 后同步 README / `quality.md` 中的测试数与覆盖率。

> **【硬性约束】GUI 截图/录屏不由 AI 伪造**
> 凡 GUI 功能变更且用户已确认实机通过，Step 5 结束前须输出「待补截图清单」并等待用户补充；
> 不得用占位图冒充、不得跳过提示。素材入库前 README 可标注「待补」并链到 `docs/screenshots/README.md`。

### Step 5.5 — 提交（Commit）

文档更新完成后，及时 git commit 当前阶段的所有变更。

- commit message 格式（P4）：`<type>(<scope>): <description>`
- type：`feat` / `fix` / `refactor` / `test` / `docs` / `chore`
- scope：变更的模块/阶段，如 `core`, `cli`, `gui`, `tests`
- 不要积攒多个阶段再一起提交
- 每阶段提交以 `Co-Authored-By: Claude <noreply@anthropic.com>` 结尾

### Step 6 — 下一步（Next）

当前阶段全部通过后：
- 对照阶段规划确认下一阶段/任务
- 向用户建议下一阶段工作内容
- 如当前阶段有遗留问题，列出并标注优先级（P0 阻塞 / P1 重要 / P2 后续）
- 启动下一轮 Step 1

## 推理侧工程组合（Inference Stack）

> 六步循环规定「做什么」，本节规定「用什么推理手段做」。
> 当前主模型：**Claude Opus 5**（Cursor Agent；长上下文 + 高强度推理 + 原生工具调用 + 子代理）。
> 组合按**任务风险分档**启用（见下方分档表），不要求每轮全开——手段本身有 token 与时间成本。

### 1. 八件手段与本仓库落地

| 手段 | 本仓库落地 | 何时必用 | 边界 / 成本约束 |
|------|-----------|---------|----------------|
| **Prompt·思维链** | 阶段模板的对抗自检 / 预死亡分析；P2 伪代码先行；疑难 bug 先写「根因假设 → 证伪路径 → 预期观测」再动手 | T2 及以上；任何「现象与代码不符」的排查 | 机械改动（补 i18n 键、重命名）不强制展开推理链 |
| **Prompt·少样本** | `docs/few-shot-examples.md` 的 ✅/❌ 成对示例；`AGENTS.md` §9 隐性规范即负例库；`AGENTS.md` 为常驻规则自动注入 | 触碰 §9 已沉淀过的领域（定界符、缩放、批量批注、编辑器对齐） | 每次踩新坑**必须回沉淀**，否则下一轮同类问题会重犯 |
| **RAG·私域检索** | 检索链固定为：`AGENTS.md` §9/§10 关键文件索引 → `docs/`（`界定符处理方案.md`、`P0–P3`、`prompts/`）→ `Grep`/`Glob` 源码 → 历史会话记录；批注私域用 MCP `mda_scan` / `mda_read_file` 结构化回灌 | 动手前一律先检索，禁止凭记忆断言代码行为 | 先查索引再全仓 Grep；外部 `WebSearch` 仅用于第三方库（CM6 / markdown-it / Electron / mermaid）API 与版本问题，结论须落到具体版本号 |
| **工具调用** | ① 校验类：`tsc --noEmit`、`npm test`、`npx playwright test`、`scripts/verify-release.js`、`scripts/ensure-no-bom.js`；② 代码解释器等价物：`node -e` 或临时脚本直接加载 `dist/core` 跑闭环；③ 产品内置探针：`state/markdown-probe.js` 一次性解析、`localStorage` 调试开关（`mda-editor-debug-inline-format` 看 `docSnap` 取材、`mda-editor-debug-click` 看落点 Δ） | 凡涉及「解析结果 / 坐标 / 渲染是否成立」的判断 | 用真实解析器与真实坐标回答，**不靠推测**；临时脚本用完即删；PowerShell 不支持 `&&` 与 heredoc，命令须分开执行 |
| **任务分解 Agent** | 三层：跨会话用 `docs/P3-*.md` 任务 DAG；会话内 3+ 步用 todo 清单；只读勘察外包给 `explore` 子代理，多步调研用 `generalPurpose` | L3 任务必须先出 DAG；跨模块链路排查优先并行派 `explore` | **写操作不并行外包**（同文件并行写会重演批量 `mda_add` 行号漂移事故，见 §9.13）；子代理只带回结论，落手改动仍由主 agent 执行，避免隐性规范丢失 |
| **多模型路由** | 推理密集（根因定位 / 架构 / 定界符算法）→ 主模型高思考档；机械批量（i18n 补键、样板测试、重命名）→ `composer-2.5` 类快模型；跨文件勘察 → `explore`；异构第二意见 → `bugbot` / `security-review` 子代理 | 出现「大量重复机械改动」或「需要独立视角复核」时 | 子代理默认 `inherit`，仅用户显式指定才换模型；触碰 `AGENTS.md` §8 禁止事项或 CM6 坐标/选取链路的改动**不得下放给快模型** |
| **输出校验** | 三层递进：① 结构/类型 —— `tsc --noEmit` + 枚举守卫 `isAnnotationLevel/Status`；② 语义不变量 —— `verifySourceProtection`（正文逐字节）、`detectEol`、渲染不可见性断言、`findMalformedAnnotations`、`repairUnrenderableSplit` 渲染探针；③ 行为 —— jest 全量 + Playwright e2e + GUI 实机 | 每轮 Step 3/4 全部执行 | **自动化全绿 ≠ 通过**：`src/gui/**` 改动仍受 Step 4 实机硬约束；模型的规划结论必须过探针，不接受自证 |
| **自我反思** | Step 3 自查 + Step 4 对抗自检 / 预死亡分析；`.cursor/l2-exam-evaluator` 作 LLM-as-judge 自评（已产出 4 轮评估报告并闭环建议）；每轮根因→修复→遗留写入 `docs/prompts/prompt-NN-*.md` | 每轮必做；用户反馈「仍有问题」时强制重走 | **改口必须附工具证据**（诊断日志 / 测试输出 / diff），不接受「再想了想应该是」；反思产出的新约束要回写 §9 与 few-shot |
| **多结果投票 / 交叉校验** | ① 路径级（已实证）：`tests/gui/editor/inline-input-sweep.test.ts` 按「五类标记 × 五落点 × 延续/取消 × 键盘/IME/IME拼音」扫 300 例，**比对三条输入路径结果一致**；② 方案级：`best-of-n-runner` 子代理在隔离 worktree 跑 N 版实现 | 高风险算法分歧（如定界符拆分策略）且验证成本低于返工成本 | 择优准则固定为「过探针 + 过 e2e + diff 最小」；**投票不替代根因定位**——多数票可能一起错（BOM 抢行首、围栏内批注这类问题只有探针能证） |

### 2. 与六步循环的对应

| Step | 必用 | 按需 |
|------|------|------|
| 1 审查 | RAG 检索链（索引 → 文档 → 源码）；`git status`/`git log` | `explore` 子代理并行勘察；历史会话检索 |
| 2 实施 | 少样本对照 §9 与 few-shot；非平凡改动先出方案待确认 | 任务分解（todo / DAG）；机械批量走快模型 |
| 3 自查 | 思维链复核算法一致性；`tsc --noEmit`；`git diff` 只改预期文件 | 内置探针定位取材文档是否被污染 |
| 4 验证 | 三层输出校验 + 对抗自检；**GUI 实机人工确认** | 多结果投票择优；`bugbot` 第二意见 |
| 5 文档 | 反思沉淀：`AGENTS.md` §9 / `few-shot-examples.md` / `docs/prompts/` | `quality.md` 校验链路、截图清单 |
| 6 下一步 | 遗留项按 P0/P1/P2 标注 | 阶段门确认是否换档 |

### 3. 按任务档位开哪几件

> 档位定义见「适用范围与阶段裁剪」§2（T0–T5）；此处只规定每档该启用哪些推理手段。

| 档位 | MDA 典型任务 | 手段组合 | 完成判据 |
|------|------------|---------|---------|
| **T0 / T1** | i18n 补键、文案；单模块 bug、CLI 输出格式 | 少样本 + RAG 索引 + `tsc` + 回归用例 | 回归用例锁定现象 |
| **T2** | 交互小增强、单模块能力扩展 | 上述 + 思维链根因假设 + 单测/集成 | 输出校验三层各至少一项 |
| **T3** | CM6 坐标/选取/定界符、写入安全、渲染预处理 | 上述 + 内置探针 + e2e + 自我反思 + **GUI 实机** | 探针与 e2e 双过 + 用户回「测试通过」 |
| **T4** | 新模块、跨层接口、算法策略选型、架构迁移 | 上述 + 任务分解 DAG + P0–P3 阶段门 + 多结果投票 | 阶段文档经用户确认后才开工实现 |
| **T5** | 可行性未知的技术探索 | 思维链 + 工具探针 + 多结果投票（原型不进主干） | POC 结论报告 |

### 4. 推理侧硬性约束

1. **不以记忆代替检索** —— 断言任何代码行为前必须有 `Read`/`Grep`/工具输出支撑；`AGENTS.md` 与代码冲突时以代码为准并回头修文档。
2. **不以「全绿」代替实机** —— `src/gui/**` 改动受 Step 4 硬约束，未获用户明确确认不得提交或推进。
3. **不并行写同一文件** —— 批注写入、同文件多处改动一律串行（§9.13）。
4. **结论改口须附证据** —— 推翻先前判断时同时给出工具证据，不做无证据的来回摇摆。
5. **投票不替代根因** —— 多数一致只是信号，不可信任度替代探针验证。
6. **每轮踩坑必沉淀** —— 新坑当轮写入 `AGENTS.md` §9 或 `docs/few-shot-examples.md`，否则视为本轮未完成。

## 阶段规划

> 以下为 **T3 完整档**的阶段定义；T0–T2 按裁剪矩阵合并或跳过，T4 在此基础上增加干系人确认与里程碑验收。
> 各阶段模板均自带「模板元信息」（版本 / 适用档位 / 裁剪指引）与「退出门禁」，按档位填写对应小节即可。

### P0 — 需求分析

**输入**：需求文档 / 命题说明 / 工单 / 缺陷报告 / 口头需求
**输出**：`docs/P0-requirements.md`
**模板**：`docs/templates/requirement.template.md`

| Step | 做什么 |
|------|--------|
| 1 审查 | 精读需求文档，提取全部显式要求 + 推断隐式约束 |
| 2 实施 | 按模板填充：背景/目标/功能描述/用户故事/验收标准/非功能需求/接口契约/假设/风险/边界/交付清单 |
| 3 自查 | 检查 Spec Self-Review 6 项；AC 必须 Given/When/Then 格式；假设标注验证状态 |
| 4 验证 | 对抗自检（3 个反向追问）；置信度评估；提交用户确认 |
| 5 文档 | P0-requirements.md 即文档 |
| 5.5 commit | `P0: 需求分析文档 — {简短主题}` |
| 6 下一步 | 进入 P1 架构设计 |

### P1 — 架构设计

**输入**：P0 需求分析
**输出**：`docs/P1-architecture.md`
**模板**：`docs/templates/design.template.md`

| Step | 做什么 |
|------|--------|
| 1 审查 | 重读 P0 非功能需求/接口契约/约束，确定技术选型边界 |
| 2 实施 | 预调研→方案对比（≥3）→推荐方案详述（Mermaid/模块影响/任务初稿）→假设→预死亡→对抗审查 |
| 3 自查 | Spec Self-Review 6 项；Mermaid 图 ≤12 节点；假设标注证据类型+置信度 |
| 4 验证 | 对抗审查 4 问题；综合置信度 ≥80%；提交用户确认 |
| 5 文档 | P1-architecture.md 即文档 |
| 5.5 commit | `P1: 架构设计 — {技术选型摘要}` |
| 6 下一步 | 进入 P2 详细设计 |

### P2 — 详细设计

**输入**：P1 架构设计
**输出**：`docs/P2-detailed-design.md`
**模板**：`docs/templates/detailed-design.template.md`

| Step | 做什么 |
|------|--------|
| 1 审查 | 重读 P1 模块影响分析 + 用户反馈，聚焦需要细化的模块 |
| 2 实施 | 核心算法（伪代码+状态机+边界表）、策略设计（原子写入/空行压缩）、CLI/GUI 规格（签名+行为+状态）、边界用例清单（E1-EN）、验证测试设计 |
| 3 自查 | 伪代码可直接翻译为代码；组件有 TS 接口定义；边界表覆盖 P0 全部 E 编号 |
| 4 验证 | 边界用例逐条对照需求文档；不可见性测试有 3 断言；提交用户确认 |
| 5 文档 | P2-detailed-design.md 即文档（含版本历史增量） |
| 5.5 commit | `P2: 详细设计 — {核心算法/策略摘要}` |
| 6 下一步 | 进入 P3 实现步骤 |

### P3 — 实现步骤

**输入**：P2 详细设计
**输出**：`docs/P3-implementation-plan.md`
**模板**：`docs/templates/dev-plan.template.md`

| Step | 做什么 |
|------|--------|
| 1 审查 | 对照 P2 模块/算法/组件，确认所有单元都有对应实现任务 |
| 2 实施 | 接口定义（完整 TS 签名）、Mermaid 架构图、任务 DAG（分 Phase/依赖/并行/文件/步骤）、预死亡分析（实施层）、回滚策略、置信度 |
| 3 自查 | 自检清单 7 项；每个任务 2-5 分钟粒度；依赖关系无循环；回滚策略可直接操作 |
| 4 验证 | 预死亡 ≥3 条含检测+回滚；不确定项标注补强方式；提交用户确认 |
| 5 文档 | P3-implementation-plan.md 即文档 |
| 5.5 commit | `P3: 实现步骤规划 — {N} 阶段 {M} 任务 DAG` |
| 6 下一步 | 进入 P4 实现 |

### P4 — 实现

**输入**：P3 实现步骤
**输出**：代码 + 测试 + 每 Phase 一次 git commit

| Step | 做什么 |
|------|--------|
| 1 审查 | 读 P2/P3 中当前任务的详细设计/伪代码/接口；`git status` + `git log` 确认干净 |
| 2 实施 | 编写代码，严格遵循 P2 规格；非平凡改动先确认方案 |
| 3 自查 | `tsc --noEmit`；`git diff` review；对照 P2 伪代码逐段检查 |
| 4 验证 | `npm test` 全部通过；手动 CLI 验证核心路径；边界/异常不崩溃；**GUI 改动须用户实机确认** |
| 5 文档 | 按 Step 5 通用清单 + GUI 附加清单更新；**GUI 改动须提示用户补截图/录屏**；记录 `docs/prompts/` |
| 5.5 commit | `P4: 实现 {模块名} (Phase {字母})` |
| 6 下一步 | 标记任务完成，启动下一个任务（按 DAG 依赖顺序） |

### P4 实现顺序

```
Phase A: 项目脚手架 (T0)
Phase B: @mda/core — model → parser → writer → renderer → barrel
Phase C: CLI — 入口 → scan → add → edit → remove
Phase D: GUI — Electron main → preload → renderer app
Phase E: 测试 — parser(25边界) → writer(原子性+压缩) → renderer(不可见性)
Phase F: 交付 — README → samples/demo.md → screenshots+video（见 docs/screenshots/README.md）→ AI协作记录
```

### P4 关键原则

1. **先编译通过，再跑测试** — 每个文件写完后立即 `tsc --noEmit`
2. **CLI 先行** — core 完成后先验证 CLI，确保 parser/writer 正确再进 GUI
3. **源文件保护** — 每次写回后验证非批注行不变（verifySourceProtection）
4. **原子写入** — 临时文件 + `fs.rename`，不直接覆盖
5. **问题即修复** — 测试失败时当场修复，不积压到下一阶段

|------|------|------|
